# Segurança e operação

## Isolamento e chaves

O guard global autentica as rotas de negócio com `Authorization: Bearer <credencial>`. Prefixos distinguem API key (`oi_live_`) de token de importação (`oi_import_`). Em ambos os casos o backend calcula SHA-256 e busca o hash; o valor bruto não é persistido. Health, Swagger/OpenAPI quando habilitados e o fallback 404 não exigem Bearer. A organização vem da credencial e queries de recursos são escopadas por ela; recursos de outra organização retornam 404. Tokens de importação só acessam rotas anotadas da sessão vinculada; nas demais (incluindo `GET .../valid-rows` e `POST|GET .../results*`), `403 AUTH.INSUFFICIENT_SCOPE`. O seed valida formato `oi_live_` + 64 hex minúsculos, guarda hash e prefixo diagnóstico, e se recusa em produção.

Há suporte a `revokedAt` na validação de chaves e de tokens de importação. Uma API key revogada não autentica e também invalida imediatamente os tokens que ela emitiu. Não existe endpoint HTTP para criar, revogar ou listar chaves, nem para revogar tokens. Não existem RBAC geral, autenticação de usuário nem auditoria completa.

CORS só controla origens autorizadas pelo navegador; não autentica clientes. Configure `ALLOWED_ORIGINS` como URLs explícitas; wildcard é rejeitado em produção.

## Logs e dados

Logs Pino fazem redaction de authorization, cookie, idempotency key, secrets, `accessToken`, hashes de credencial, chaves S3, `WEBHOOK_SECRET_ENCRYPTION_KEY`, `secretCiphertext` e o header `OpenImport-Signature`. `X-Request-ID` permite correlacionar resposta e `traceId`; envie-o em chamados de suporte, não uma API key, token de importação, segredo de webhook ou conteúdo CSV. URLs de webhook são logadas sem query, userinfo ou fragmento. Bodies de delivery não entram em logs.

CSV pode conter dados pessoais. Use fixtures sintéticas, limite acesso a logs e storage e evite copiar linhas de clientes para tickets. Mensagens de erro de preview não ecoam valores de célula.

## Saúde e dependências

`/health` é liveness. `/health/ready` verifica em paralelo PostgreSQL, Redis e bucket S3/MinIO (HeadBucket, PING, `SELECT 1`) com timeout limitado por dependência (`HEALTH_PROBE_TIMEOUT_MS`). Ao expirar o timeout, um `AbortSignal` cancela HeadBucket no AWS SDK e encerra imediatamente a conexão efêmera do probe Redis (`disconnect` + `resetAndDestroy` no socket); a promise tardia permanece observada para evitar unhandled rejections. O probe PostgreSQL respeita o sinal antes/depois de `isReady()`, mas a query Prisma em voo não é cancelável de forma nativa. Qualquer falha ou timeout responde `503 HEALTH.NOT_READY` com mensagem genérica; logs internos podem registrar nomes estáticos (`postgres`, `redis`, `object_storage`) sem URLs ou credenciais. O probe não cria bucket, não publica jobs e não limpa Redis.

As credenciais do `docker-compose.yml` são fracas e exclusivamente locais. Elas não são referência de produção.

## Storage, fila e ciclo de vida

CSV é salvo fora do PostgreSQL em storage S3 compatível; banco guarda metadata e chave interna, nunca exposta pela API. Em falha de parse após storage, o backend tenta apagar o objeto e marca a sessão como `upload_failed`. Confirmação enfileira processamento em Redis/BullMQ; retries são limitados (`IMPORT_WORKER_MAX_ATTEMPTS` + backoff). Execuções falhas não retêm `ImportRecord`. Payload normalizado e CSV não entram em logs. Um reconciliador no mesmo processo republica jobs órfãos ou divergentes (BullMQ `failed`/`completed` com execução ainda não terminal), sem criar novas execuções (`IMPORT_JOB_RECONCILE_INTERVAL_MS`, paginação por cursor). Ready bem-sucedido insere `webhook_deliveries` pending na mesma transação se houver endpoint ativo, com snapshot de URL, payload e ciphertext do segredo; o POST assinado corre na fila `webhook-delivery` após o commit (`WEBHOOK_WORKER_MAX_ATTEMPTS`, timeout curto, sem redirects). Cada tentativa resolve o hostname **uma vez**, valida todos os endereços e conecta só ao IP pinado, preservando o hostname original em `Host` e SNI/certificado TLS (`rejectUnauthorized` permanece o padrão; nunca `false`). Não há segunda resolução DNS. PUT/DELETE do endpoint afetam só eventos futuros; o worker descriptografa o ciphertext da delivery (AAD v2 `organizationId:endpointId`; blobs v1 sem prefixo `v2.` continuam sem AAD após o backfill). Destinos são validados contra SSRF (só HTTPS em produção; loopback/privado/link-local/metadata/IPv4-mapped bloqueados). `WEBHOOK_SSRF_ALLOW_PRIVATE_TARGETS` é rejeitado em produção. O segredo de assinatura é cifrado em repouso com `WEBHOOK_SECRET_ENCRYPTION_KEY` (64 hex) e revelado só no PUT. Em desenvolvimento local as filas usam Redis DB 0; a suíte E2E usa DB 15 e só limpa esse namespace (`obliterate` no setup/teardown) — não use `FLUSHALL`/`FLUSHDB` no DB de desenvolvimento.

Após `ready` ou `processing_failed`, o CSV original deixa de ser necessário para `valid-rows`, rejected-rows ou results. O cleaner `ImportFileRetentionCleaner` (mesmo processo Nest; timer desligado em `NODE_ENV=test`) remove objetos rastreados por `storageObjectKey` depois de `IMPORT_FILE_RETENTION_HOURS`, usando `ImportExecution.finishedAt` como relógio. A listagem de candidatos usa o índice parcial `idx_import_executions_file_retention` em `(finished_at, import_session_id)`. Concorrência multi-instância usa claim/lease (`storageCleanupClaimedAt` + `storageCleanupClaimToken`); delete S3 ocorre fora de transação PostgreSQL; conclusão CAS grava `storageDeletedAt` e anula a key. Logs de retenção só carregam IDs/status/resultado — nunca object key, filename ou CSV. `upload_failed` não entra nesta política (a key nunca é persistida nesse status). Órfãos no bucket sem pointer no DB ficam para lifecycle nativo do storage. Sessão, execução, `ImportRecord`, results e webhook deliveries **não** são apagados. DLQ completa fica para uma fatia futura.

## Riscos para exposição pública

Antes de publicar, faltam ao menos modelo de usuário, gestão segura de chaves, rate limiting, retenção/eliminação de sessões no PostgreSQL, estratégia de backup e proteção de dados. O token de importação reduz o risco de expor a API key no navegador, mas não substitui hardening público completo. Webhooks `import.ready` são assinados (HMAC-SHA256) e sujeitos a SSRF; o consumidor ainda precisa verificar assinatura, janela de replay e dedupe. Retenção de CSV no object storage cobre apenas objetos rastreados após estados terminais elegíveis.
